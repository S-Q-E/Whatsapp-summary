# WhatsApp AI Secretary — рефакторинг в веб-сервис

## Что это
Локальный сервис для врача. Читает её WhatsApp (Baileys, read-only), находит
в переписках ОБЕЩАНИЯ ВРАЧА («посмотрю анализы вечером»), отслеживает их
выполнение, показывает веб-дашборд и в 18:00 присылает дайджест в её же
WhatsApp («чат с собой»). Это не summarizer: цель — «что врач должна сделать».

## Текущее состояние
Рабочий MVP: Node 20+, TypeScript ESM, Baileys 7, Drizzle + better-sqlite3,
Fastify API + SSE, React-дашборд (Vite + Tailwind), Docker (multi-stage),
провайдеры AI (openrouter/ollama/heuristic/mock), транскрибация голосовых,
CLI-скрипты analyze/digest/eval, 170+ тестов проходят. Мы НЕ переписываем
с нуля, а поэтапно исправляем и расширяем. Не удаляй рабочий код без причины,
описанной в отчёте.

## Известные проблемы (подлежат исправлению по шагам)
1. Задачи сопоставляются по тексту названия (includes/equals):
   повторная задача с тем же названием молча теряется (skipped),
   «Позвонить» и «Позвонить в лабораторию…» склеиваются.
2. В промпт не передаётся whatsapp_message_id, поэтому source_message_id
   от модели недостоверен. Обновление задач идёт по matchTitle, а не по id.
3. Время в промпте в UTC; границы дня зависят от TZ процесса.
4. Контекст анализа — только сообщения за один день; анализ без
   инкрементальности (нет processed-флага).
5. AutoProvider навсегда залипает на эвристике после первой ошибки.
6. Не обрабатываются: обёрнутые сообщения (ephemeral/viewOnce),
   правки/удаления, соответствие LID↔номер телефона, голосовые.
7. analyze/digest — отдельные CLI, нет единого процесса и планировщика.
8. Схема в BOOTSTRAP_SQL, без версионированных миграций.

## Стек (целевой)
Node 20+, TypeScript strict, ESM; Drizzle + better-sqlite3 с настоящими
миграциями; zod для конфигурации и ответов LLM; Fastify (API + раздача
статики); Vite + React + Tailwind для фронтенда (mobile-first, русский язык);
node-cron/внутренний планировщик; тесты — node:test (как сейчас) или vitest,
но не смешивать.

## Жёсткие правила
- WhatsApp: сервис ТОЛЬКО читает. Единственное разрешённое исходящее —
  дайджест на OWNER_JID. Любая отправка проходит через один модуль
  sendGuard, который отклоняет всё, кроме OWNER_JID. Проверяется тестом.
- Данные пациентов — медицинские. Тексты сообщений не пишем в логи
  (кроме debug при LOG_MESSAGE_CONTENT=true). Веб-интерфейс по умолчанию
  слушает 127.0.0.1 и требует авторизацию. Секреты только в .env.
- Задачи сопоставляются по id, а не по тексту. Тексты названий для
  идентификации не использовать никогда.
- Все пользовательские тексты (UI, дайджест) — на русском.
- Время: единая TIMEZONE из .env. Внутри хранится UTC ms epoch, в промпт и в
  UI время выводится в локальной зоне со смещением.
- Никаких заглушек и TODO вместо логики. Чего не смог сделать — скажи явно.
- Не меняй публичные контракты шагов, которые ещё не начаты.

## Как работать в каждой сессии
1. Прочитай AGENTS.md и файлы, затронутые шагом. Составь короткий план.
2. Сначала пиши падающие тесты на то, что чиним, потом код.
3. В конце обязательно: npm run typecheck && npm test, покажи результат.
4. Итоговый отчёт: что изменено, какие файлы, что НЕ сделано, риски,
   как мне вручную проверить. Не начинай следующий шаг без моей команды.

## Правила проверки
- Каждый багфикс начинается с падающего теста, воспроизводящего баг.
- Тесты запускаются командой npm test; новые файлы тестов добавляются
  в скрипт test автоматически (используй glob tests/*.test.ts, не список).
- Не расширяй область изменений за пределы промпта. В отчёте перечисли,
  что изменено, и что осталось нерешённым.
